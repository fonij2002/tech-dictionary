مستندات را تا حد ممکن نزدیک به موضوعی نگه دارید که آن را توضیح می‌دهند، عنوان‌های واضح انتخاب کنید و به‌جای صفحات بسیار طولانی و همه‌منظوره، صفحات کوچک و متمرکز بسازید.

## Frontmatter

هر صفحه باید یک عنوان داشته باشد. اضافه کردن description نیز به‌شدت توصیه می‌شود:

```md
---
title: احراز هویت API
description: نحوه پیکربندی و استفاده از احراز هویت API.
---
```

فیلدهای اختیاری مفید شامل `draft`، `sidebar`، `tableOfContents` و `template` هستند.

## سازمان‌دهی براساس هدف

یک ساختار کاربردی می‌تواند به این شکل باشد:

```text
src/content/docs/fa/
├── getting-started.md
├── tutorials/
├── guides/
├── reference/
└── concepts/
```

فقط زمانی directory جدید بسازید که navigation را واضح‌تر می‌کند. Starlight می‌تواند sidebar را مستقیماً از همین ساختار فایل‌ها تولید کند.

## لینک‌ها

برای لینک دادن بین صفحات مستندات، لینک‌های نسبی را ترجیح دهید:

```md
[دیپلوی](./deployment/) را ببینید.
```

لینک‌های نسبی باعث می‌شوند سایت هنگام دیپلوی شدن زیر subpath مربوط به GitHub Pages نیز قابل حمل باقی بماند.

## مثال‌های کد

از fenced code block همراه با شناسه زبان استفاده کنید:

````md
```ts
export function greet(name: string) {
  return `Hello ${name}`;
}
```
````

## صفحات پیش‌نویس

می‌توانید صفحات ناقص را داخل repository نگه دارید بدون اینکه در production منتشر شوند:

```md
---
title: قابلیت آینده
draft: true
---
```

صفحات draft از production build حذف می‌شوند.

## چه زمانی از MDX استفاده کنیم؟

به‌صورت پیش‌فرض از Markdown ساده استفاده کنید. فقط زمانی MDX را وارد کنید که یک صفحه واقعاً به componentهای importشده یا نمایش غنی‌تر نیاز دارد. componentهای قابل استفاده مجدد در `src/components/content/` قرار می‌گیرند. برای الگوی پیشنهادی، [کامپوننت‌های سفارشی](./custom-components/) را ببینید.
